# 長任務 vs 現行 Pipeline：客觀品質評估

日期：2026-07-30
方法：真實搜尋 + 自動硬指標 + 盲評 LLM judge（thinking），兩組實體（`scripts/eval-long-task-quality.ts`）

---

## 1. 硬指標（兩者皆全部通過）

| 指標 | 現行多段 | 長任務 | 結論 |
|---|---|---|---|
| 生產 schema 驗證 | ✓ | ✓ | 平手 |
| Citation 白名單命中率 | 100% | 100% | 平手 |
| 有引用的維度比例 | 100% | 100% | 平手 |
| 分數-勝者邏輯一致性 | 100% | 100% | 平手 |

**在正確性與結構可靠性上，長任務與現行 pipeline 完全同等。**

## 2. 內容深度（長任務明顯較淺）

| 指標 | 現行 | 長任務 | 差距 |
|---|---|---|---|
| 平均 summary 長度（Notion 組） | 140 字元 | 103 字元 | **−26%** |
| 平均 summary 長度（iPhone 組） | 187 字元 | 87 字元 | **−53%** |
| Verdict 長度 | 664 / 713 | 475 / 508 | **−28%** |
| 具體數據點比例（iPhone 組） | 9/18 | 4/18 | **現行 2.25×** |
| Pros/Cons 條目數 | 18 / 26 | 16 / 20 | 略少 |

模式清晰：**主題越資料密集（iPhone 規格、價格、數據），長任務丟失的具體細節越多**；概念性主題（Notion）差距較小。

## 3. 盲評 Judge（兩組一致）

| 面向（0–10） | Notion 組 現行/長任務 | iPhone 組 現行/長任務 |
|---|---|---|
| Faithfulness（忠實於來源） | **9** / 8 | **9** / 7 |
| Specificity（具體數據） | **6** / 5 | **9** / 6 |
| Completeness（完整深度） | **7** / 6 | **9** / 7 |
| Balance（兩邊平衡） | 7 / **8** | 9 / 8 |
| **總分** | **7** / 7 | **9** / 7 |

兩組 judge 均判現行勝出，差距主因是 faithfulness 與 specificity——長任務在單次生成中會「概括化」，傾向寫出合理但較空泛的敘述；分段分析則迫使模型對每個維度單獨挖掘數據。

## 4. 成本 vs 品質的最終天平

| | 現行多段 | 長任務（no-think） |
|---|---|---|
| Token 成本 | 基準 | **−43%** |
| Wall time | 基準 | −18%（略快） |
| 結構可靠性 | 100% | 100%（同） |
| 內容深度/具體性 | **較好**（judge 9 vs 7，數據點 2.25×） | 較淺 |
| 適用場景 | **品質優先（預設）** | 成本敏感/高流量/簡單實體 |

## 5. 客觀結論

1. **長任務在「省 43% 成本」的同時付出可量測的品質代價**：內容深度 −26~−53%、具體數據點減半、judge 總分 9→7（資料密集主題）。
2. **正確性沒有妥協**：schema、citation、邏輯一致性全部 100% 通過，差的是「深度與具體性」而非「錯誤」。
3. **對本產品的建議**：CompareAI 的核心價值是「有數據支撐的深度對比」，品質差距直接影響產品價值——**維持現行多段 pipeline 為預設**。
4. **可選的務實用法**：
   - 長任務作為 `AI_PIPELINE_MODE=long-task` 的成本敏感模式（高流量、簡單實體、A/B 測試）
   - 或在長任務 prompt 中硬性要求「每維度至少引用 2 個具體數據點」再測——可能縮小 specificity 差距（未驗證，值得低成本一試）

## 附：評估方法的客觀性說明

- 硬指標為程式計算，無主觀成分
- Judge 採盲評（隨機對調報告順序，judge 不知道哪份是哪種方法產出），兩組實體交叉驗證
- 每組僅一次生成，存在單次方差；但兩組方向一致且幅度明顯，結論穩健
